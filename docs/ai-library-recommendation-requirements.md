# 首页 AI 组件库检索与推荐方案

- 状态：方案草案
- 日期：2026-09-24
- 相关文档：[领域词汇](../CONTEXT.md) · [ADR 0005](./adr/0005-one-shot-library-recommendation.md)
- 决策说明：本方案拟替换 ADR 0005 的“结构化条件 + 等权计分”机制；确认后应新增 ADR 记录替代关系。

## 1. 目标

首页保留现有目录、搜索、筛选和排序，并增加“AI 帮我选”入口。

用户用一句自然语言描述项目需求，系统从数据库中的组件库里返回最多 3 个候选，帮助用户进入详情页继续判断。推荐对象始终是组件库（代码实体为 `Library`）；`components`、`blocks` 和 `templates` 只是交付类型。

本方案优先保证：

1. 不违反用户明确提出的硬性条件；
2. 推荐结果与自然语言需求相关；
3. 推荐依据来自数据库中的真实资料；
4. AI 或语义检索故障时可以安全降级。

## 2. 为什么调整旧方案

旧方案把用户需求解析为少量标签，再按命中数量等权计分。当前生产目录有 45 个组件库，多数库在价格、源码、访问方式、交付类型和使用场景上高度相似。

对现有数据的模拟结果显示：

- 77.1% 的条件组合会出现第一名并列；
- 52.1% 的条件组合会有超过 3 个库并列；
- 只有 5 个库设置了 `featuredRank`，但它们会在大量同分场景中主导结果。

因此，继续调整标签权重不能稳定解决推荐质量问题。新方案改用开源搜索社区常见的“两阶段检索”模式：先召回可能相关的候选，再使用专用模型精确重排。

## 3. 选定方案

```text
用户需求
   ↓
识别明确的硬性条件
   ↓
过滤不符合条件的组件库
   ↓
关键词检索 + 语义检索
   ↓
合并两个检索结果
   ↓
专用重排模型重新排序
   ↓
程序复核并返回 Top 3
```

方案组成：

- **硬条件过滤**：保证明确条件不会被推荐结果违反；
- **关键词检索**：匹配名称、标签和简介中的明确词语；
- **语义检索**：理解“企业后台”和“管理系统”等不同说法之间的语义关系；
- **结果融合**：使用 RRF 合并关键词和语义排名；
- **候选重排**：使用专用 reranker 判断需求与候选资料的相关性；
- **程序复核**：再次检查硬条件、候选身份和返回数量。

## 4. 核心原则

- 推荐直接使用数据库中的原始资料，不维护 AI 生成的“推荐卡片”；
- 大模型只负责识别明确条件和请求类型，不直接选择组件库；
- 硬性条件只使用数据库中经过维护的结构化字段；
- embedding 和 reranker 只影响相关性排序，不能绕过硬性条件；
- 推荐理由只能引用结构化字段或原始简介，不允许生成新的事实；
- `featuredRank` 不参与有明确需求时的主要排序；
- 推荐状态与目录筛选、排序和 URL 相互独立；
- 推荐故障不得影响目录、收藏和详情访问。

## 5. 功能范围

### 5.1 包含

- 单次自然语言输入；
- Clerk 登录后提交；
- 识别 `pricing`、`source`、`access`、`delivery` 和 `useCases` 的明确包含或排除条件；
- 检索名称、简介、标签、用途和视觉风格；
- 关键词与语义混合检索；
- 候选重排并返回最多 3 个结果；
- 展示命中的结构化条件和原始资料依据；
- 输入校验、限流、功能开关、错误处理和降级；
- 中文和英文界面文案。

### 5.2 不包含

- 多轮对话、聊天历史或会话恢复；
- 自动放宽硬性条件；
- 根据收藏或历史行为进行个性化；
- 运行时访问官网、GitHub 或其他站外资料；
- AI 生成组件库事实或推荐卡片；
- 独立向量数据库；
- 用户级行为分析、漏斗归因或 A/B 实验；
- 通用问答、代码生成或指定组件库对比。

## 6. 推荐数据

### 6.1 原始资料

每个组件库的检索内容由以下数据库字段组成：

- 名称和简介；
- `pricing`、`source` 和 `access`；
- `delivery` 和 `useCases`；
- 标签；
- 经人工维护的视觉风格（如实现该字段）。

运行时数据库仍是唯一事实来源。AI 推断结果不能写回组件库资料，也不能变成硬条件事实。

### 6.2 搜索索引

为每个组件库维护一条搜索索引记录，至少包含：

- `libraryId`；
- 用原始字段拼接得到的检索文本；
- 检索文本哈希；
- embedding；
- embedding 模型版本；
- 更新时间和索引状态。

组件库资料发生变化后，将索引标记为过期并重新生成。索引过期期间，该组件库仍可参加结构化过滤和关键词检索，但不使用旧 embedding 参加语义检索。

当前只有 45 个组件库，首版直接在应用内计算相似度，不引入 Qdrant、OpenSearch 等独立服务。目录规模明显增长后再评估迁移。

## 7. 推荐流程

### 7.1 请求理解

模型把自然语言转换为严格的结构化结果：

- 请求是否属于组件库推荐；
- 明确要求包含的硬条件；
- 明确要求排除的硬条件；
- 用于关键词和语义检索的原始需求。

只有“必须”“只能”“不能”“不要”等明确表达才形成硬条件。无法确定时保留为搜索需求，不得猜成硬条件。

模型不能输出候选 ID、slug、分数或推荐结果。所有输出必须通过 Schema 校验；`undisclosed` 不能成为用户条件。

### 7.2 硬条件过滤

- 同一维度中的多个允许值按 OR 处理；
- 不同维度按 AND 处理；
- 排除条件命中时移除候选；
- 未知值不能满足硬性条件；
- 没有符合条件的候选时，不自动放宽条件。

### 7.3 混合检索

对通过硬条件过滤的组件库执行两种检索：

1. 关键词检索：根据原始检索文本中的词语和标签排序；
2. 语义检索：根据用户输入与组件库原始资料 embedding 的相似度排序。

使用 RRF（Reciprocal Rank Fusion）合并两个排名。RRF 使用排名位置而不是直接混合两套不同量纲的分数，首版不设置未经评测的手工权重。

融合后保留最多 12 个候选进入重排。

### 7.4 候选重排

使用固定版本的专用 reranker，对“用户需求 + 候选原始资料”进行相关性评分。中英文首版可以评估 `BAAI/bge-reranker-v2-m3`，但业务接口不能绑定具体模型。

reranker：

- 只能对召回候选重新排序；
- 不能增加候选或生成事实；
- 不能修改硬条件；
- 失败时退回 RRF 排名。

### 7.5 最终复核

服务端在返回结果前必须：

1. 确认候选真实存在；
2. 再次检查全部硬性条件；
3. 移除没有有效相关性信号的候选；
4. 最多保留 3 个结果；
5. 同分时按 RRF 名次，再按 slug 稳定排序。

`featuredRank` 只用于没有有效搜索需求时的编辑精选，不得作为正常推荐的首要破同分依据。

## 8. 推荐结果

每个结果至少展示：

- 组件库名称和详情入口；
- 命中的结构化条件；
- 与需求相关的标签、用途或简介片段；
- 无法确认但可能影响选择的信息。

不展示看似精确的“匹配百分比”。推荐说明由服务端根据真实字段和原始文本生成，不让模型自由编写。

如果最高候选没有足够的相关性依据，系统提示用户补充用途、风格或交付类型，而不是返回由 `featuredRank` 决定的任意结果。

## 9. 用户与交互

- 所有用户都可以看到推荐入口，只有已登录用户可以提交；
- 未登录提交时触发 Clerk 登录，不保存输入草稿；
- 每次提交都是独立请求，不携带历史状态；
- 用户修改原始描述后重新提交；
- 推荐结果不读取或修改目录筛选、排序和 URL；
- 推荐区域复用现有响应式页面，不建设独立聊天界面。

## 10. 鉴权、安全与隐私

- 推荐 API 使用 Clerk session 鉴权；
- 单条输入最多 2,000 个字符；
- 初始限流为每用户每 10 分钟 10 次、每日 30 次；
- 查询解析、embedding 和 reranker 使用独立配置；
- 所有模型输出都必须经过 Schema 或数值范围校验；
- 组件库资料按数据而非指令传入模型，防止提示注入；
- 数据库、日志、监控和错误报告不保存原始输入；
- 只记录聚合请求量、错误率、耗时、模型用量和估算成本；
- 上线前确认模型供应商不将输入用于训练，并采用零保留或最短保留期。

## 11. 失败降级

- 条件解析失败：不执行推荐，提示用户重试；
- 语义检索失败：使用硬条件过滤和关键词检索；
- reranker 失败：使用 RRF 融合排名；
- 索引过期：该库不使用旧 embedding，但仍可参加其他检索；
- 所有检索都无有效结果：返回“暂无匹配结果”；
- 功能开关关闭：隐藏入口，传统目录继续可用；
- 所有失败都不得修改目录状态。

## 12. 测试与发布门槛

建立不少于 50 条中英文固定样例，覆盖：

- 明确包含和排除条件；
- 模糊使用场景和视觉描述；
- 中英文同义表达；
- 无匹配、信息不足和越界请求；
- 条件解析、语义检索或 reranker 故障；
- 索引过期和数据缺失。

发布必须满足：

- 硬性条件违反率为 0；
- 推荐只包含数据库中真实存在的组件库；
- 展示的依据全部可以追溯到原始字段；
- 混合检索的 Top 10 召回率优于纯关键词基线；
- 重排后的 Top 3 质量优于未重排结果；
- 相同模型和索引版本下结果可重复；
- 降级路径、鉴权、限流和功能开关经过自动化测试；
- `bun test`、`bun x ultracite check` 和生产构建通过。

检索质量使用 Recall@10、MRR 或 NDCG@3 等标准指标评估。权重、候选数量和最低相关性阈值必须根据固定样例调整，不能仅凭经验设置。

## 13. 实施顺序

1. 整理组件库原始检索文本，并建立中英文固定样例；
2. 实现搜索索引、文本哈希和 embedding 批量生成脚本；
3. 实现请求理解和确定性硬条件过滤；
4. 实现关键词检索、语义检索和 RRF 融合；
5. 接入 reranker、最终复核和失败降级；
6. 实现推荐 API、鉴权、限流和功能开关；
7. 实现首页输入、结果列表和推荐依据展示；
8. 完成离线评测、隐私检查和生产数据审计后受限开放。

## 14. 开源方案参考

- [Qdrant Hybrid Queries](https://qdrant.tech/documentation/search/hybrid-queries/)：稀疏与稠密检索、RRF 和多阶段查询；
- [OpenSearch Hybrid Search](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/index/)：关键词与语义检索、结果归一化和搜索管道；
- [Sentence Transformers Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)：候选召回后使用 CrossEncoder 重排；
- [FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding)：多语言 embedding 与 reranker；
- [Haystack Evaluation](https://docs.haystack.deepset.ai/docs/evaluation)：检索组件和完整管道评测。

## 15. 后续阶段

以下能力在首版稳定后单独评估：

- 独立搜索或向量服务；
- 更多经过人工维护的推荐维度；
- 实时访问官网或 GitHub 获取最新资料；
- 多轮澄清、条件编辑和显式放宽；
- 用户反馈、个性化和产品价值实验。
